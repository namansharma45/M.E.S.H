# MESH UI — NO VIBE CODE RULES

These rules are mandatory. They carry forward the anti-vibe direction previously used for Alfred, adapted to MESH's industrial engineering context.

## 1. Visual direction

MESH should look like a serious engineering/research console.

Use:

- strong typography;
- restrained colors;
- neutral/industrial visual language;
- clear hierarchy;
- whitespace;
- subtle borders;
- minimal shadows;
- compact, purposeful controls;
- real status indicators;
- static or restrained motion only when it communicates state.

## 2. Absolutely avoid

### No gradients

Especially:

- purple gradients;
- violet/lavender gradients;
- rainbow gradients;
- neon/electric-blue gradients;
- glowing background blobs.

### No neon/glow aesthetic

Avoid:

- electric blue/cyan/neon blue;
- pink/magenta accents;
- glowing borders;
- luminous text;
- sci-fi HUD styling.

### No glassmorphism

Do not use:

- frosted glass panels;
- excessive blur;
- transparent floating cards;
- glowing translucent containers.

### No generic SaaS styling

Avoid:

- huge hero headings;
- "AI-powered", "revolutionary", "next-generation", "intelligent future" copy;
- excessive pill-shaped labels;
- card grids where a table or simple section is clearer;
- dashboard templates that look interchangeable with finance/marketing SaaS.

### No novelty fonts

Use one strong, readable interface font family unless a documented accessibility requirement says otherwise.

Do not use:

- sci-fi fonts;
- futuristic display fonts;
- novelty handwritten fonts;
- multiple unrelated font families.

### No decorative fake data

Never use a chart, gauge, number, status, or badge merely because it looks good.

### No fake AI visualizations

Do not add:

- neural-network animations;
- fake "AI activity";
- fake model thinking indicators;
- fake live telemetry;
- fake confidence meters;
- decorative data streams.

### No excessive containers

Avoid turning every sentence or value into a rounded card.

### No unnecessary animation

Do not use:

- bouncing elements;
- constant motion;
- typewriter effects;
- particles;
- animated backgrounds;
- decorative 3D objects;
- transitions that distract from measurements.

## 3. Copy rules

Use direct engineering language.

Good:
- "RUL estimate"
- "Sensor unavailable"
- "Prediction interval"
- "Model version"
- "Dropped modality comparison"
- "Source window"

Bad:
- "Your machine's future, unlocked"
- "AI brain"
- "Predictive magic"
- "Next-gen industrial intelligence"
- "Dashing analytics"
- "Revolutionary insight"

## 4. Every UI element needs a reason

Before adding a component, answer:

1. What engineering question does it answer?
2. What data source feeds it?
3. What action does the engineer take because of it?
4. What happens if the value is unavailable?

If these cannot be answered, do not add the component.

## 5. Industrial readability

Prioritize:

- readable axis labels;
- units;
- timestamps;
- run identifiers;
- clear missing-state indication;
- legible tables;
- consistent decimal precision;
- accessible contrast.

## 6. MESH must not pretend

The UI must clearly distinguish:

- measured data;
- model prediction;
- uncertainty;
- experiment result;
- unavailable data.

The visual design should make that distinction obvious.
